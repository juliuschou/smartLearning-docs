# 前後端開發 WBS 與先後順序 — 智學互動平台

> 依據：`../20_系統分析/`（M01–M11 需求與驗收規格）、`../30_系統設計/ER模型設計.md`（含 `er_model_postgresql.sql`）、`../80_系統雛形/`（M01–M11 互動雛形，作為 UI 行為基準）。
> 詞彙依 `../20_系統分析/GLOSSARY.md`。資料庫：PostgreSQL。

## 0. 技術基調（定案）

- **技術棧**：前端用 Next.js、後端用 NestJS、資料庫用 PostgreSQL，全部用 TypeScript 一種語言寫到底。
- **後端**：用 NestJS 提供 API（一般查改用 REST）、即時推播走 Socket.IO 通道；資料庫是 PostgreSQL，表格結構就用已定稿的 `er_model_postgresql.sql`。心跳、Game PIN 流水、控制權這種高速存取的東西，未來想加速可以加 Redis，但一開始先用 PostgreSQL 的條件式唯一索引就夠了。NestJS 順便用 `@nestjs/swagger` 自動產生 API 說明文件，前端直接拿來用。
- **前端**：Next.js（App Router）做兩個各自的網站，共用一組「呼叫 API 的程式碼」（由後端 OpenAPI 自動產生，搭配 openapi-typescript ＋ SWR/TanStack Query）：
  - 管理端（對應雛形的 `index.html`）：給系統管理者和老師用（M01–M07、M09、M10）。
  - 學員端（對應雛形的 `learner.html`）：給不用申請帳號的學員（M08），另含投影畫面（projection，只收訊息不送）。
- **即時推播**：後端用 NestJS 的 WebSocket Gateway（Socket.IO），前端包一層連線用戶端。學員端的心跳、「可以作答了」「公布結果了」都靠它即時推；老師控制台即時收到三個人數數字與回應。雛形裡「按 L 模擬失聯跳安全待機畫面」是前端自己斷線時的畫面行為，不是後端功能。
- **安全界線**：所有「你有沒有權限做這件事」的判斷都在後端做——NestJS Guard 檢查登入 Session 裡存的權限快照；前端（包含 Next.js 後端渲染的部分）把選單藏起來只是讓畫面好用，不算防線（雛形已註明）。學員的匿名憑證存在 httpOnly cookie（JavaScript 讀不到），不放 localStorage。
- **專案結構**：一個倉庫管全部（monorepo，用 pnpm workspace）：`apps/admin` 管理端、`apps/learner` 學員端、`apps/api` 後端、`packages/api-client` 共用 API 呼叫端、`packages/db` 共用資料庫存取套件。

## 1. 里程碑總覽（先後順序）

| 里程碑 | 內容 | 前面要先做完 | 對應模組 |
|---|---|---|---|
| MS0 | 把環境弄好：資料庫表格、自動檢查（CI）、後端骨架、兩端共用的 API 約定 | 無 | —（打地基） |
| MS1 | 帳號、角色、權限的基本盤（含邀請/重設密碼用的一次性連結） | MS0 | M01/M02/M04、M03（管理老師帳號） |
| MS2 | 題庫管理 | MS1 | M05 |
| MS3 | 教學活動管理（含把題目「影印」進活動的快照、Game PIN 加入資訊） | MS2 | M06 |
| MS4 | 核心互動整條路：學員加入→作答→老師控制→統計與公布（含組隊競賽） | MS3 | M07/M08/M09、M11（團隊模式） |
| MS5 | 系統設定與營運監控、批次操作、報表匯出（P1）、組織競賽（P1） | MS4 | M03 批次、M10、P1 |
| MS6 | 整合驗收、安全檢核、上架部署 | MS5 | 全部 |

**為什麼照這個順序**（跟著 ER 模型的先後關係）：
先把「人的基本盤」立起來（帳號→角色→權限→誰有什麼權限→系統參數），再立「題目的來源」（題庫），最後才做「上課發生的事」（活動→作答→計分→公布）。每一步做完都能單獨驗收，而前一步做好的 API 正好是後一步拿來測試的工具。

## 2. 後端 WBS

### MS0 共同基礎（1.0）
- 1.1 先把 `er_model_postgresql.sql` 在空的資料庫上跑一遍，確認所有表格建得起來，而且每個欄位都有說明文字（用 `\d+` 檢查）；同時建立資料庫變更的管理方式（migration），之後改表格只能「加」不能「刪」。
- 1.2 把後端的骨架立好，先講好大家共用的規矩：出錯時回覆的格式固定、錯誤訊息一律模糊化（例如不能讓人試出「這個帳號存在」）、同一件事重複送不會重複做（冪等）、查清單要分頁、避免兩人同時改同一筆資料互相覆蓋（版本鎖）。
- 1.3 後端用 NestJS 的 `@nestjs/swagger` 自動產生 API 說明文件（OpenAPI），名稱一律照 GLOSSARY 的用詞；前端拿這份文件自動產生呼叫 API 的程式碼（`packages/api-client`），兩邊講同一種話。
- 1.4 設定 CI 自動檢查：程式碼風格檢查（lint）＋單元測試＋拿一個全新的資料庫把 SQL 從頭到尾跑一次（必須一次成功）。
- **5.X 驗證慣例**：每一小步做到一段落就先跑相關測試，需要連資料庫的整合測試用拋棄式容器臨時開一個乾淨環境來測（做法見測試規範）。

### MS1 帳號與授權（2.0）
- 2.1 做好「一次性連結」表格（`one_time_link`），三種用途共用：寄邀請、忘記密碼、Email 驗證。邀請連結 7 天內有效、重設密碼連結 30 分鐘內有效；重新寄一次，舊的連結就作廢；同一個信箱 60 秒內不再寄第二封。
- 2.2 做登入（M01）：帳號密碼打錯時一律回同一句模糊的訊息（不能讓人試出帳號存不存在），試幾次都不鎖帳號；登入後發一組 Session 記錄，裡面存下「這個人現在有哪些權限」的快照（jsonb）；另有登出、太久沒動自動登入失效、忘記密碼。
- 2.3 管理帳號（M02/M03）：新增/修改/查詢/停用老師帳號（採邀請制，先寄邀請連結）；一停用帳號，他正在用的 Session 馬上失效；並實作「建立第一個系統管理者帳號」的流程（照指引文件）。
- 2.4 管理角色與權限（M02/M04）：角色、功能權限是固定目錄；設定某個角色有哪些權限時，一次送出整份清單、一次全換掉（要嘛全成、要嘛全不變），同一份重複送不會出錯；屬於 P1 尚未開放的權限不能指派；要測清楚「改權限要重新登入才生效」跟「停用帳號立刻失效」這兩種情況。
- 2.5 系統參數（M10 前半）：把活動的預設設定、Session 多久沒動就失效，做成可設定的參數；批次修改時用版本鎖，避免兩個人同時改互相蓋掉。
**驗收證據**：停用的帳號登不進去；權限改了之後，還沒重新登入的人拿舊權限去用新功能會被擋；快照存的權限內容跟實際角色權限比對一致。

### MS2 題庫（3.0）
- 3.1 管理題庫（M05）：老師可以建自己的題庫，裡面放題目、選項、標籤；題目可以查、加、改、刪；刪掉是「軟刪除」（還救得回來）；整份題庫可以複製一份副本（副本名稱會自動加上流水號）；每種題型要檢查規則（例如選項數量、正解數量合理）。
- 3.2 權限邊界測試：老師只能看到、只動得到自己的題庫，別人的碰不了。
**驗收證據**：刪掉的題目不會再出現在清單、但救得回來；複製副本後原題完全不動。

### MS3 教學活動管理（4.0）
- 4.1 建立活動（M06）：老師挑題庫組一堂課；建立時套用系統參數的預設值，之後改參數不會回頭影響已建立的活動；活動的參與模式、排行榜模式要先檢查互相搭不搭得起來；活動狀態只能一路往前（未開始→進行中→已結束），不能倒退。
- 4.2 題目快照：選好題目後，把題幹、題型、選項文字、正解、題序整份「影印」存在活動底下；之後老師改了或刪了原題庫，這堂課用的還是當時的版本；快照跟活動建立包在同一筆資料庫交易裡完成，不會存到一半。
- 4.3 加入資訊：產生 6 位數 Game PIN（開頭可以是 0）加 QR code／連結，一組一起用；重新產生時整組一起換新、舊的整組作廢，不能只換一半。
- 4.4 活動控制（M07 前半）：提供查詢活動狀態、每道題的狀態、三種公布各自狀態的介面；可以開始/結束活動；每次重要操作都寫進活動事件記錄（誰、何時、做了什麼）。
**驗收證據**：建完活動後去改題庫，活動裡的題目內容不變（前後比對）；舊的 PIN 用不了。

### MS4 核心互動閉環（5.0，最關鍵）
- 5.1 學員加入（M08）：學員不用申請帳號；用 PIN 加入後，暱稱可以自己取也可以不取（不取就由系統配一個）；發給學員一支猜不出來的私鑰（存在瀏覽器裡），斷線了拿它重新加入；學員定期送心跳（60 秒內有跳就算在線）。
- 5.2 即時通道：把所有學員的心跳彙整起來算在線人數；老師按「開放作答」「停止作答」、公布結果時，學員端和投影畫面會即時收到通知；學員端看到統計時只有答案分布，看不到哪個是正確答案。
- 5.3 老師控制台（M07）：開放/停止作答；不能跳到下一題之後又跳回前一題；同一個活動同一時間只有一位老師有控制權（控制租約，用資料庫唯一索引保證）；搶到/失去控制權也都記進活動事件。
- 5.4 作答提交（M08）：同一個學員同一題重複送不會重複算（用 client_submission_id 分辨）；開放期間內可以改答案重送，以最後一次成功的為準；沒趕上的（遲到的）不收。
- 5.5 統計（M09）：某道計分題一開放作答，就把當時有資格作答的學員（或隊伍）名單「拍成一張快照」，這張名單就是統計的分母；後來遲到的、觀看未參與的人都不補進去；各選項多少人答，重算後存起來當報表加速用；在線人數、已加入人數、已作答人數這三個數字分開算、分開顯示，不混用。
- 5.6 計分與排行榜（M09）：個人答對得 100 分、沒答對 0 分，每題比重相同；排名有兩種算法——同分並列、下一個跳號（1,1,3）vs 同分並列、下一個不跳（1,1,2），由活動設定決定用哪種；有資格的人數為 0 時顯示「不適用」不硬算；活動設定不顯示排行榜時，老師還是看得到彙總結果。
- 5.7 團隊模式（M11）：可以設定要分組、分幾隊；一鍵隨機分組、可自訂隊名、可手動調人；老師按下確認分組的那一刻就鎖定，之後不能再改；一個學員同一時間只會在一隊；每題每隊只結算一次（重複要求結算不會加第二次分）；隊伍分數由隊員資格人數攤算。個人模式可以先做，TEAM 模式在這一段完成。
- 5.8 公布（M07/M09）：公布分四種——統計、正解、個人排行榜、隊伍排行榜，各自獨立公布；公布出去就收不回來（撤不回）；有錯要更正時是出「新版本」，且必須填寫更正原因。
**驗收證據**：兩個人同時搶控制權只有一個成功；同一題同一隊重複結算只有一筆生效；公布之後試著撤回做不到（系統根本沒有這個功能）；排名演算法照表訂例子測都對。

### MS5 營運與 P1（6.0）
- 6.1 批次管理（M03）：批次操作要嘛全部完成、要嘛全部不動（做到一半失敗就整批退回）；同一批操作重複送不會重做。
- 6.2 系統監控（M10）：批次更新系統參數；提供營運監控頁面；連線狀態查不到時顯示「未知」，不亂猜。
- 6.3 P1 功能（預設關閉，用開關控制）：報表匯出成 CSV/XLSX；組織（跨單位競賽比較）。
- 6.4 觀測性：日誌用固定格式、每筆帶請求編號方便追蹤、絕不把密碼或憑證寫進日誌；做一個定期清掃的排程工作，把過期的心跳和沒人用的控制租約清掉。
**驗收證據**：批次做到一半失敗就整批退回原狀；同批重複送，結果跟送一次一樣。

### MS6 驗收與部署（7.0）
- 7.1 端到端驗收：把 M01–M11 的驗收規格一條一條實測；E2E 測試腳本照雛形的「試用流程」來寫。
- 7.2 安全檢核：一項一項確認沒登入、權限不夠的請求都被擋（不在權限目錄裡的功能一律拒絕）；學員私鑰要夠亂、猜不出；Game PIN 要擋暴力嘗試；掃一遍日誌確認沒漏任何敏感資料。
- 7.3 部署：寫好資料庫變更的執行順序與回退步驟；接上監控訊號，出事能第一時間知道。

## 3. 前端 WBS

### F0 共同
- F0.1 做共用的「呼叫後端用戶端」（`packages/api-client`，由 NestJS 的 OpenAPI 自動產生），加上 WebSocket 連線的封裝（Socket.IO）：斷線自動重連、連不上就顯示「安全待機」畫面；同時做資料庫存取共用套件（`packages/db`，用 Drizzle 或 TypeORM，以 `er_model_postgresql.sql` 為基準）。
- F0.2 做好共用的讀取中/錯誤訊息元件（呈現後端回的模糊化訊息）；API 版本一改就跟後端約定好同步升級。
- F0.3 視覺基準：直接拿系統雛形 `80_系統雛形` 的 style.css 當初稿，只重構不重新設計。

### F1 管理端 App（`apps/admin`，Next.js，對應 index.html）
- F1.1 登入頁＋外框：登入後左側選單照這個人的權限顯示/隱藏（只是使用體驗，真正的把關還是在後端）。
- F1.2 帳號維護頁（M02/M03：新建/編輯/啟停用老師帳號）＋權限設定頁（M04：某個角色的功能打勾清單，一次整批儲存）。
- F1.3 題庫頁（M05）：軟刪除/復原/複製的按鈕跟流程、一題一題編輯的表單——雛形沒做完整，這裡正式實作。
- F1.4 活動建立精靈（M06）：一步步挑題庫→確認快照→產生 PIN/QR；設定不搭時自動提示。
- F1.5 控制台（M07）：三個數字（在線/已加入/已作答）分開顯示；開放/停止作答按鈕；公布統計/正解/排行榜的操作；模式已鎖定的提示；另做投影畫面（對應 projection.html）。
- F1.6 報表頁（M09）：排行榜的競賽排名/密集排名切換；匯出按鈕。
- F1.7 系統設定頁（M10：批次表單＋版本鎖提示「別人已改過請重載」）＋批次操作進度顯示（M03）。

### F2 學員端 App（`apps/learner`，Next.js，對應 learner.html；行動裝置優先）
- F2.1 加入流程：輸 PIN 或掃 QR → 取暱稱（可以不取）→ 等待開始的畫面。
- F2.2 作答：作答開放期間內可以改答案重送；老師公布後，只看得到答案分布，看不到正解。
- F2.3 斷線重連：私鑰存在瀏覽器裡，斷線後自動重連；連不上進「安全待機」畫面；公布結果會即時跳出來。

## 4. 前後端開發對應表（含順序編號）

> 編號就是建議的施工順序：每個編號都是「先做後端、再做前端、最後驗收」的一條小完成線；同一編號裡的東西要一起完成，不同編號之間可以視人力平行做。
> 規格編號對照 `../20_系統分析/Mxx` 各文件的「功能範圍」表（例如 M01-01＝使用者登入）；P1 等級的功能（M09-07 匯出、M11-12～15 組織競賽）先延到順序 8 才做。

| 順序 | 階段 | 後端任務（NestJS） | 前端任務（Next.js） | 對應模組與規格編號 | 工時預估（後端＋前端，人日） | 怎麼算完成 |

**工時怎麼估的（假設說明）**：
1. **人日**：一位稱職工程師做一個工作天；含這段的單元測試和自己先驗證過，不含跨段的整合驗收（那筆在順序 9）。

3. **難的部分已加在裡面**：順序 5 和 7（多人同時操作、重複結算、公布收不回）已經放比較高的測試比重；如果團隊第一次用 NestJS 的即時通道，順序 5 再多留 2–3 人日餘裕。
4. **P1 可以延**：順序 8 裡的 P1 功能（M09-07、M11-12～15）大約占 5 人日，整包往後挪也不影響主線。
5. **這是規模感不是報價**：用來排程和配人手即可；建議做完順序 2，照實際速度把後面重估一次。

## 5. 排程原則備註

- **先做後端**：每個里程碑完成時，後端就要先交付一組能自己測的 API（NestJS ＋ OpenAPI 文件），前端接著把畫面接上這組 API；唯一允許當作「重大變更」處理的事情就是 API 合約改動——合約一變，要在 CI 自動比對 OpenAPI 差異，明確標出來。
- **一個倉庫管全部**：專案用 pnpm workspace ＋ Turborepo 管理（後端 `apps/api`、管理端 `apps/admin`、學員端 `apps/learner`、共用 API 呼叫端 `packages/api-client`、共用資料庫套件 `packages/db`），在順序 1（MS0）就把骨架立好。
- **最容易出錯的一段**：順序 5–7（MS4）——控制權限、資格快照、重複結算、公佈收不回來這幾件事最容易在多人同時操作時出包。建議這幾段至少兩個人一起看過程式碼，並且做多人在線同時操作的壓力測試；涉及計時（心跳、租約到期）的測試一律用一個測試程式一口氣跑完，不要分段手動點（見測試環境規範）。
- **怎麼算驗收通過**：拿 `20_系統分析` 每個模組的驗收規格一條條對照，加上 `80_系統雛形` 已經做對的規則清單當逐條檢查表；雛形本身可以當示範腳本，用它演一遍跟正式系統對照。
