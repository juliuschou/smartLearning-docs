# M2 系統分析與設計 — 文件交付計畫

> [!info] 目的
> 本檔為「智學互動平台」M2 系統分析與設計階段的文件交付計畫,保存供執行時參考。M2 要將 M1 已定案的可觀察需求轉成可實作的系統設計,並消解各基線列出的「M2 設計輸入」與 BDD 紅卡。

## Context

「智學互動平台」M1 已完成:7 份需求基線(P0-01~07)+ 3 份 BDD 場景 + 1 份關聯圖 + 技術棧初稿。M2(預計 2026-08-24 前)要將這些可觀察需求轉成可實作的系統設計,並消解各基線列出的「M2 設計輸入」與 BDD 紅卡。

現況:`20_系統分析/`、`30_系統設計/`、`50_實作與測試/`、`60_交付成果/` 均為空。`40_技術棧/技術棧.md` 有基礎決策(Next/Nest/Prisma/PostgreSQL/Win11)但大量項目標「待 M2 確認」。

**已確認的技術方向(使用者決策):**
- 即時通訊:Socket.IO(Nest.js Gateway,單機滿足 300 人)
- 部署:單機 Docker Compose(Next+Nest 同機,Nginx 反向代理,PostgreSQL 同機)
- 密碼雜湊:Argon2id
- 前端狀態:React Query + Zustand
- DB 並發:Prisma + PostgreSQL optimistic version / row lock(不全域 SERIALIZABLE)
- Redis:僅用於 Socket.IO adapter + rate limit(DB 為權威)
- 監控:Pino structured log + 基礎 metrics
- 壓測:Artillery + Socket.IO client 模擬
- open text 呈現(文字列表/文字雲/切換):**標紅卡並繞過**,不阻擋其餘 M2

**核心原則:** M2 文件消解紅卡(給具體設計決策),不重新定義需求規則 —— 每條規則 link 回上游基線的單一權威來源。

## 二、`30_系統設計/` 文件

### 3. 資料模型與 ER 設計.md

**目的:** 定義 Course/LiveSession ER Model、題目與快照模型、匿名參與者、Submission、idempotency、結果歸檔及刪除事件的儲存設計。M2 設計基石。

**主要 H2:**
- 設計原則與識別碼策略
- 核心 ER Model
- Course 與 LiveSession 儲存模型
- QuestionDefinition、Option 與 SessionQuestion 快照
- User、WebSession 與 Participant
- Submission、Idempotency 與結果彙總
- ArchivedResult、Retention 與刪除事件
- 索引、唯一約束與部分索引
- Transaction、Lock 與 Optimistic Concurrency
- Prisma Mapping 與 Migration 邊界

**Mermaid:** `erDiagram`、`sequenceDiagram`(Submission 寫入與聚合更新、SessionQuestion close、Archive finalize)

**關鍵設計決策:**
- 平台產生 UUID 為主識別碼。
- Session code 用 CSPRNG 產生,輸入轉大寫後查詢,保留全歷史唯一索引。
- `LiveSession.expires_at` 支援 8 小時 hard limit。
- Course 未結束場次用 PostgreSQL partial unique index。
- `SessionQuestion` 另存 immutable snapshot,不依賴後續 `QuestionDefinition`。
- `SessionQuestionOption` 與 `QuestionDefinitionOption` 分開,避免快照被來源題目修改。
- `Submission`:`(participant_id, session_question_id)` unique constraint + idempotency key/payload hash 欄位。
- Submit 與 close 都鎖同一 `SessionQuestion` row,DB commit 順序為唯一線性化點。
- Course 題目排序採 `version` optimistic concurrency control。
- 不用全域 `SERIALIZABLE`;用 row lock、unique constraint 與必要重試降低衝突成本。
- `ArchivedResult`/`ArchivedAnswer` 不保存可回連 display name 或 participant token 的關聯。
- retention 與提前刪除留不含答案內容的 tombstone/audit event。

**消解紅卡:** Course/LiveSession/QuestionDefinition/Option/SessionQuestion 儲存模型、session code 亂數/碰撞/索引/到期、participant token hash 與場次隔離、Submission unique constraint/idempotency/transaction isolation、Course 題目排序併發、ArchivedResult/90天 retention/提前刪除/tombstone、backup restore 防復活資料邊界。

### 4. Web Auth 與安全設計.md

**目的:** 定案 Web 帳號、bootstrap、Cookie Session、CSRF、密碼、step-up、rate limit 及 Participant/CLI credential 的安全實作。M2 核心交付。

**主要 H2:**
- 威脅模型與安全邊界
- 帳號、角色與授權模型
- Bootstrap 與帳號建立
- Argon2id 密碼雜湊與臨時密碼
- DB-backed Web Session
- Cookie、CSRF 與 Origin 防護
- 登入、登出、改密碼與 Session 失效
- Step-up Authentication
- Account 與來源雙重 Rate Limit
- Participant Token 與重連驗證
- CLI Credential 與 Windows Credential Store
- 安全錯誤、稽核與不記錄資料

**關鍵設計決策:**
- 密碼 Argon2id,M2 固定參數、升級策略與 benchmark 依據。
- Web Session 用 DB opaque token hash;Cookie 僅存不可逆 session value。
- Cookie `Secure`/`HttpOnly`/`SameSite=Lax` + `__Host-` 前綴。
- cookie-authenticated mutation 要求 CSRF token + `Origin` 檢查。
- `auth_epoch`/`credential_version` 讓停用、改密碼、管理員 reset 立即失效全部 Session。
- Bootstrap 只能在 DB 無管理員時執行;秘密不進 command line/shell history,採 Docker secret/互動式 stdin。
- CLI MVP 僅 Windows 11,credential 存 Windows Credential Manager;不承諾跨 OS fallback。
- Participant token 高熵 opaque,DB 只存 hash,不寫 log。
- Redis 僅分散式 rate limit;帳號與 Web Session 權威在 PostgreSQL。

**消解紅卡:** bootstrap 命令與秘密傳遞、Web Session 儲存與 cookie 形式、CSRF/SameSite/Origin、Argon2id 演算法與參數、密碼 reset/臨時密碼/force change、step-up 10 分鐘、帳號+來源雙重 rate limit、participant token 格式/保存/重連驗證、CLI credential 儲存與 header 傳遞。

### 5. API 與共用 Schema 設計.md

**目的:** 定義 Web、Participant、CLI/Agent 共用的 API、wire schema、response envelope、錯誤模型、validation token 與 idempotency 契約。M2 核心交付。

**主要 H2:**
- API 版本與共用 Wire 規約
- Request／Response Envelope
- 錯誤碼、欄位 Path 與可重試資訊
- Web Auth 與管理 API
- Course、Question 與 Batch API
- LiveSession、Participant 與 Submission API
- Result Query、Archive 與 Delete API
- CLI Command 與 Agent Host 邊界
- Question Schema Versioning
- Validation Token、Payload Hash 與 Preview
- Idempotency 與安全重試
- Endpoint 授權與 Transaction Boundary
- OpenAPI／Schema 產出與相容策略

**API 範圍:** `/api/v1/auth/*`、`/api/v1/users/*`、`/api/v1/courses/*`、`/api/v1/courses/{courseId}/questions/*`、`/api/v1/live-sessions/*`、`/api/v1/live-sessions/{sessionId}/submissions`、`/api/v1/results/*`、Socket.IO handshake 與 event payload。

**CLI command:** `auth configure`、`auth status`、`courses list`、`questions validate`、`questions create`(不提供 `--yes`/`--force` 跳過 preview/確認)。

**共用 envelope:**

```json
// 成功
{ "data": {}, "meta": { "schema_version": 1, "request_id": "..." }, "error": null }
// 錯誤
{ "data": null, "meta": { "schema_version": 1, "request_id": "..." },
  "error": { "code": "FIELD_FORBIDDEN", "path": "questions[2].correct_option_refs",
             "message": "...", "blocking": true, "next_step": "..." } }
```

**關鍵設計決策:**
- 批次 validation 一次回報所有 error/warning。
- `schema_version: 1` 為 MVP 版本。
- payload hash:canonical JSON 後 SHA-256。
- validation token:opaque,綁定 actor/key/course/payload hash + 15 分鐘期限。
- `Idempotency-Key` 與 request payload hash 一起保存;相同 key 但 hash 不同回傳衝突,不覆寫原結果。

**消解紅卡:** endpoint 與 response envelope、題目 wire schema 與版本相容、Web/CLI validation parity、CLI command 最終形式、validation token/payload hash/期限、批次 all-or-nothing/preview/確認、Question create transaction 與安全重試、Submission idempotency API、權限重查與穩定錯誤碼。

### 6. 即時同步與結果治理設計.md

**目的:** 定義 Socket.IO 連線、房間、事件順序、snapshot/replay、重連、背壓、即時彙總、歸檔與 retention 流程。M2 核心交付。

**主要 H2:**
- Socket.IO 與 Nest Gateway 架構
- Namespace、Room 與連線認證
- Event Contract 與事件序號
- Snapshot、Replay 與重連
- Submit、Aggregate 與 Broadcast 流程
- Submit／Close 競態與權威順序
- Backpressure、Coalescing 與超量行為
- LiveSession Close 與 ArchivedResult
- 90 天 Retention Job
- 提前刪除、稽核事件與 Tombstone
- Open Text 呈現紅卡
- 即時同步與結果治理的失敗恢復

**關鍵設計決策:**
- Nest.js Gateway 用 `/live` namespace。
- Room:`session:{liveSessionId}`(必要時分離 `teacher:{sessionId}` 與 `participant:{sessionId}`)。
- 事件:`session.snapshot`、`session.state_changed`、`question.opened`、`question.closed`、`result.updated`、`session.closed`、`sync.required`。
- 每事件含 `event_seq`/`aggregate_version`/`server_timestamp`/`schema_version`。
- 伺服器保存短期 event outbox;重連以 `last_event_seq` replay,無法補齊回傳完整 snapshot。
- Submission 寫入、彙總更新與 outbox 事件同一 transaction。
- 廣播可合併頻繁 `result.updated`,但不得合併或遺失 Submission commit。
- Socket.IO 事件非權威;重連與 REST snapshot 以 PostgreSQL 為準。

**open text 紅卡:** M2 只定案純文字輸入/長度驗證、不接受 HTML/Markdown、API 輸出安全編碼、權限/匿名化/retention 規則、即時結果不洩露不符合 vote-to-reveal 資料。文字列表/文字雲/切換列為非阻擋紅卡。

**消解紅卡:** Socket.IO 技術與 Nest Gateway、房間/廣播/事件順序/snapshot-replay/重連、backpressure/coalescing/rate limit/過載、Submission 與 close DB 線性化、即時彙總與 ArchivedResult 一致性、8h 自動 closed 與手動 close 共流程、retention job 重試/失敗告警/idempotency、提前刪除 preview/確認/transaction/audit、backup restore 防復活、open text 非阻擋呈現紅卡。

### 7. 架構、容量與可觀測性設計.md

**目的:** 定案單機 Docker Compose 拓撲、資源與連線池預算、Redis 角色、超載行為、監控與壓測執行方式。

**主要 H2:**
- MVP 部署拓撲
- Docker Compose 服務與健康檢查
- 單場 300 人容量預算
- PostgreSQL 連線池與資源配置

- Structured Logging 與 Metrics
- Dashboard 與 Alert
- 壓測工具與資料生成
- Browser／Profile 測試矩陣
- M4 測試報告輸入

**部署拓撲:**

```text
Nginx
 ├── Next.js Web
 └── Nest.js API + Socket.IO + Scheduler
       ├── PostgreSQL
       └── Redis
```

**關鍵設計決策:**
- 單機 Docker Compose;Nginx 反向代理 + TLS termination。
- Nest.js、Socket.IO Gateway 與 8h scheduler 先在同一 API container。
- PostgreSQL 為所有狀態/Session/Submission/結果/稽核權威來源。
- Redis 納入 Compose,MVP 僅 rate limit counter + Socket.IO adapter,不作資料/帳號狀態唯一來源。
- DB connection pool、request timeout、Socket connection 上限、Redis memory limit 列入容量表。
- 觀測:Pino structured log + request id + API latency histogram + Socket connection/event/reconnect metrics + DB pool/transaction retry/queue backlog metrics。
- 壓測 Artillery 或等效 Socket.IO client,覆蓋 W1~W8。
- Browser matrix:Windows 11 Chrome 最新穩定版 + Edge 最新穩定版;行動瀏覽器只做響應式 smoke,不作完整 300 人效能承諾。

## 五、M2 文件完成驗收標準

1. **Frontmatter 與格式:** 每檔 title/type/status/created/updated/tags/project 齊全;H1 對應 title;H2/H3 層級正確;callout 類型正確;wikilink 可解析;Mermaid 可渲染。
2. **Wikilink 完整性:** 上游 wikilink 指向現有文件;heading anchor 用實際標題;首頁可反向連到所有 M2 文件;無 orphan note。
3. **單一來源:** P0 狀態與業務規則不在設計文件重定義;效能數值只引用 [[MVP 效能目標]];題型/validation 只引用 [[題目領域契約]];retention/刪除只引用 [[結果資料治理]];設計文件只補資料表/API/交易/事件/部署/監控決策。
4. **跨文件一致性:** ER entity 名 ↔ API resource 名;API 欄位 ↔ Question schema;API error code ↔ 題目契約 error code;Socket.IO event 名 ↔ API/狀態名;User role/`can_create_course`/Course ownership ↔ Auth matrix;Submission/idempotency/aggregate ↔ 歸檔流程;每個狀態轉換有允許角色/前置條件/transaction boundary/成功事件/失敗 error code。
5. **紅卡閉環:** Web Auth/ER/snapshot/unique constraint/wire schema/validation token/payload hash/idempotency/Socket.IO/reconnect/replay/backpressure/retention/提前刪除/backup restore/Compose/Redis/pool/metrics/壓測 全部有具體決策;只有 open text 視覺呈現可標「非阻擋、延後產品決策」。
6. **Mermaid 與可讀性:** Obsidian Preview 確認每張 stateDiagram/erDiagram/sequenceDiagram 可渲染,entity/欄位/actor/API/event 與正文一致,圖表說明狀態/資料流/交易邊界而非裝飾。
7. **三方審查:** PO/BA(是否忠實引用 P0、無未核准需求)、Developer(是否足以開始 Prisma/Nest/Next/Socket.IO 實作)、QA/Tester(能否推導狀態/競態/重連/idempotency/容量驗收案例)各審一次。完成後才把首頁 M2 標完成並進入 M3。
