# 角色專屬首頁實作計畫

## Context
目前登入後的 role routing 不完整：student 已有 `/student` 與「我的課程」，但 admin 的預設目的地 `/admin` 沒有 page route，teacher 沒有專屬 route/layout，teacher 仍會落到 public starter `/`。本次依據本目錄的 `角色專屬首頁實作計畫.md`，完成最小、可驗證的三角色 landing slice；不提前實作尚未有前端契約的課程管理、live session 或 dashboard 統計。

## Success criteria
- `/admin` 由既有 admin shell 保護，提供清楚標題/說明與 `/admin/accounts/new` CTA。
- `/student` 與 `useMyCourses()` 的 student-only query gate、loading/error/empty/data 四態維持不變。
- `/teacher` 有獨立 protected layout 與 landing view，只顯示 `SessionDto` 的 `displayName`、`username`、`role`、`canCreateCourse`。
- 無 `next` 的登入預設導向為 admin `/admin`、student `/student`、teacher `/teacher`。
- `mustChangePassword` 在登入、role layout 與 force-change 完成後的導向中優先於 `next`/role check；forced teacher change 最終導向 `/teacher`。
- 未登入或錯誤角色在 children render 前導向 `/login?next=<encodeURIComponent(pathname)>`；既有單斜線 `next` 驗證與 open-redirect 防護不退化。
- 三個 role shell 都保留 `/settings/password` 及既有 `LogoutButton` 流程；public `/` 不改用途。
- 不修改 backend、schema、API client/query contract，不加入 mock/placeholder API 資料或新依賴。

## Existing contracts and patterns to reuse
- `lib/auth/session.ts` 的 `useSession()` 是唯一 session authority；`SessionDto` 已包含本 slice 所需全部欄位。
- `app/(admin)/layout.tsx` 與 `app/(student)/layout.tsx` 的 gate 順序固定為：loading placeholder → `mustChangePassword` redirect → missing/wrong-role redirect → shell。
- `components/auth/LogoutButton.tsx`、`Link` to `/settings/password`、Tailwind shell/header，以及 server page 的 `Metadata`/`h1` pattern。
- `features/student/MyCoursesView.tsx` 與 `test/my-courses-view.test.tsx` 保持現狀，作為 student regression baseline。
- Next 16 route groups 不出現在 URL；teacher 必須使用 sibling group `app/(teacher)/teacher/page.tsx`，不能把 page 放在既有 admin/student group 下。

## Implementation steps

### Checkpoint A — lock routing behavior with regression coverage
1. In `features/auth/LoginForm.tsx`, update the role fallback in `resolveNext()` to add an explicit `teacher → /teacher` branch. Keep `admin → /admin`, `student → /student`, invalid/unknown role → existing defensive `/` fallback, and preserve the current same-origin relative `next` checks.
2. In `features/auth/ChangePasswordForm.tsx`, update `roleHome()` to map `teacher → /teacher`, while retaining `admin`, `student`, and defensive unknown-role fallback behavior. Do not change voluntary-change behavior.
3. Update `test/login-form.test.tsx` so the teacher default assertion expects `/teacher`, and add/retain coverage proving `mustChangePassword` ignores `next`.
4. Extend `test/change-password-form.test.tsx` with a forced teacher session that receives a rotated non-forced session and redirects to `/teacher`; keep the existing forced-student and voluntary-change assertions.

### Checkpoint B — add the missing role routes/views
5. Add `app/(admin)/admin/page.tsx` as a static server page with metadata, an accessible `h1`, a short admin description, and a `Link` named for `/admin/accounts/new`. Do not duplicate the CTA in `app/(admin)/layout.tsx` unless implementation review shows the page cannot be reached clearly from the shell.
6. Add `app/(teacher)/layout.tsx` as a client component mirroring the existing shell pattern, but requiring `session.role === "teacher"`:
   - loading → existing `載入中…` placeholder;
   - `session?.mustChangePassword` → `redirect("/settings/password")` before role validation;
   - missing/wrong role → `redirect(`/login?next=${encodeURIComponent(pathname ?? "/teacher")}`)`;
   - valid teacher → teacher header, settings link, `LogoutButton`, and children.
   Use a teacher-specific shell label while keeping the raw contract role available in the landing view.
7. Add `app/(teacher)/teacher/page.tsx` as a server page shell with metadata and a clear `h1`, importing only the teacher feature view.
8. Add `features/teacher/TeacherHomeView.tsx` as a client component using only `useSession()` (no `apiRequest`, fetch, query key, hook, or fabricated data). Render the session display name, username, raw role value (`teacher`), and a clear localized create-course capability status for both `true` and `false`. The layout is authoritative for access; a defensive null-session branch may return no content rather than inventing a loading/API state.
9. Leave `app/(student)/student/page.tsx`, `features/student/MyCoursesView.tsx`, enrollment hooks, `app/page.tsx`, and backend files unchanged.

### Checkpoint C — focused regression tests
10. Add `test/admin-home.test.tsx` to verify the page exposes its heading/description and a link to `/admin/accounts/new` without requiring an API call.
11. Add `test/teacher-home-view.test.tsx` with mocked `useSession()` states covering display name, username, role, `canCreateCourse=true`, `canCreateCourse=false`, and no API request/mock data path.
12. Add `test/teacher-layout.test.tsx` with `useSession()`/`next/navigation` mocks covering:
    - loading does not render children;
    - `mustChangePassword` redirects even when the session role is wrong;
    - missing session and wrong role redirect without rendering children;
    - redirect destination encodes the current pathname and uses `/teacher` fallback;
    - valid teacher renders the shell, `/settings/password` link, logout control, and children.
    Make the redirect mock throw a sentinel so tests prove protected children cannot leak before the redirect. Reuse the existing QueryClient and navigation-mocking conventions.
13. Keep `test/my-courses-view.test.tsx` as the student regression check; it already proves active-roster data, empty/error states, and no `/me/courses` request for non-students.

## Risk, rollback, and scope controls
- **Risk: medium** — login/force-change destinations and a new authorization shell are security-sensitive, but no persistence or backend contract changes are involved.
- **Guardrails:** copy the established gate order exactly; test wrong-role/must-change precedence; preserve `encodeURIComponent`; render only session-proven fields; do not generalize the duplicated layouts in this slice.
- **Rollback:** remove the new admin/teacher route, view, and tests; restore the two teacher fallback branches in `LoginForm.tsx` and `ChangePasswordForm.tsx`. No migration, seed, cookie, or backend rollback is required.
- Preserve the pre-existing unrelated working-tree modification in `tasks/todo.md`; do not rewrite or fold it into this slice.
