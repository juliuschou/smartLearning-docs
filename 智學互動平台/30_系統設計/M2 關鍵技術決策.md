## 1. Identity：UUID v7（取代 BIGINT identity）— 已定案

DB 綱要文件目前全表用 `BIGINT GENERATED ALWAYS AS IDENTITY`，僅 `submission.idempotency_key` 為 UUID（DB §假設與待 M2 確認）。規劃 Phase 0 明文要求修正此衝突後才建 Prisma schema（規劃 L52）。

**決策**：

- 所有 PK/FK 改用 UUID。
- 採 **UUID v7**（時序可排序，利於 B-tree index locality 與插入效能）。
- 產生方式：**應用層產生 UUID v7、寫入時帶值**（不依賴 DB 端 `gen_random_uuid()`，因其產 v4 不具時序性）。Prisma model `id String @id`，應用層於 create 時帶入。
- `submission.idempotency_key` 維持 UUID，由 client 產生。
- Prisma 對 PostgreSQL UUID 對應為 `String`。

**理由**：API/DB identity 一致（規劃）；避免可列舉序號洩漏資料量級；UUID v7 時序性降低隨機 UUID 的 index 碎片。

**影響**：Phase 2+ 所有 model 的 `id` 與 FK 皆為 `String`（UUID v7）。需新增 UUID v7 產生 helper（`src/common/crypto` 或獨立 `src/common/identity`）。

## 2. 狀態表達：TEXT + CHECK — 已定案

**決策**：所有狀態欄位用 `TEXT + CHECK`，不採 PostgreSQL native `ENUM`。

**理由**：DB 綱要文件已明確假設 TEXT+CHECK（DB L586-590）；ENUM 變更（增刪值）需 migration 且剛性高，TEXT+CHECK 較可逆、符合「expand-first」遷移原則。

**實作**：

- Prisma schema 以 `String` 對應，應用層以 union type / const object 守護合法值。
- CHECK constraint 由手寫 raw SQL migration 補（Prisma 不直接支援 CHECK，需 `prisma migrate dev --create-only` + 手寫 SQL）。

**影響**：Phase 2+ 各狀態欄位（`account.status`、`course.status`、`live_session.status`、`session_question.status`、`question_definition.type` 等）依此模式。穩定狀態碼定義於應用層 domain module。

## 3. Lock protocol：FOR UPDATE 同一 SessionQuestion row + READ COMMITTED — 方向已定，待 Phase 6 驗證

**決策**（基線）：Submit 與 close 都先對同一 `session_question` row 執行 `SELECT … FOR UPDATE`，使用 `READ COMMITTED`，DB transaction commit 順序為唯一線性化點（DB L406-423、M2 §2.6）。

- 不用全域 `SERIALIZABLE`；採 row lock + unique constraint + optimistic version + 必要重試（M2 §2.3）。
- Submit 先 commit：答案保留。close 先 commit：後續答案拒絕。auto-close 與 manual close 共用同一 application command 與 lock order。

**待驗證**：Phase 6 以真 PostgreSQL 多連線 contention benchmark 驗證 submit p95 ≤ 500ms（效能目標 W2/W6/W7）。**不達標才在設計階段改採 advisory shared/exclusive lock 或 optimistic version，不在實作中臨時改語意**（規劃 L56）。

**本次**：只記錄決策，不實作 lock helper（Phase 1 僅建 transaction/lock helper 骨架，Phase 6 實作競態並測）。

## 4. Web Session：PostgreSQL-backed opaque session — 已定案

**決策**：

- PostgreSQL 為帳號與 Web Session 唯一權威；Cookie 只放高熵 opaque token，DB 存 `cookie_hash`（DB web_session L105-122）。
- Cookie 屬性：`__Host-` prefix、`Secure`、`HttpOnly`、`SameSite=Lax`。
- cookie-authenticated mutation 需 CSRF token + `Origin` 檢查（M2 §2.4 L177-180）。
- 期限：30 分鐘 idle、8 小時 absolute；高風險 admin/CLI key operation 需 10 分鐘內 step-up（P0-03、M2 §2.4 L186）。
- session rotation、全 session revocation transaction；停用/重設/改密碼立即撤銷。

**理由**：M2 §2.4 已定方向；不引入 JWT/Passport，以本地 application code + PostgreSQL 實作（規劃 Dependencies L155）。

**影響**：Phase 2 實作 `WebSession` model、cookie options builder、CSRF/Origin guard、step-up guard。

## 5. Argon2id：固定預設參數，benchmark 留 Phase 2/9 — 方向已定，待驗證

**決策**：

- 密碼雜湊採 Argon2id。
- 預設參數：`m=64MiB, t=3, p=1`（OWASP 基準）。
- 實際資源調校與 W1-W8 實測列為 Phase 2/9 驗證工作（M2 L367-369）。

**影響**：Phase 2 引入 `argon2` 套件、`PasswordHasher`（位 `src/common/crypto` 或 identity module），記錄參數與升級策略。

## 6. Validation token：opaque + DB record（不採 signed token）— 已定案

**決策**：題目 batch validation 採 **DB-backed opaque validation token**，不採 signed token。

- token 為 opaque，綁定 actor/key/course/payload hash，期限 15 分鐘（M2 §2.5 L224-229）。
- DB 存 token hash（與 session 同模式），不引入簽章金鑰管理。
- confirm 時重送 payload、重驗 hash/授權/validation；同 idempotency key 回原結果。
- idempotency record 只在正式 command 建立，取消不留下待處理資料（規劃 L55）。

**理由**：M2 文件只規定 opaque + 綁定資料，未要求簽章格式或演算法（M2 §2.5）；DB-backed 模式與 Web Session 一致，降低金鑰管理複雜度。

**影響**：Phase 3 實作 `QuestionBatchCommand` model 與 validation token 流程；preview/confirm API。

## 7. 題目排序併發：advisory lock — 已定案

**決策**：Course 題目 append/reorder 採 `pg_advisory_xact_lock(hashtext('qdef:' || course_id::text))` + 同交易內 `MAX(position)+1`（DB L235-241）。

**理由**：DB 綱要文件已定方案；transaction-scoped advisory lock 序列化同 course 並發附加，避免 position 衝突。

**影響**：Phase 3 實作；Phase 1 的 `TransactionService` 提供 advisory lock helper 骨架。

## 8. can_create_course scope + CLI credential revocation — 已定案

**決策**：

- `can_create_course` 是 account-level flag，由 admin 控制（US-F16）。
- **移除旗標只阻止新建 Course，不撤銷既有 Course 管理權**（保留既有 Course/題目/歷史結果）（規劃 L57、US-F16）。
- **CLI credential 撤銷不與 `can_create_course` 旗標連動**，為獨立流程，由 admin 透過 revoke CLI credential 流程處理。
- 帳號 disable 立即撤銷相關 CLI credential 與未用 token（P0-03）。

**理由**：M2 文件未提 CLI revocation 方案，不將 Web 的 credential version 直接推定為 CLI revocation（M2 §2.4 L186）。分離降低耦合。

**影響**：Phase 2 Auth matrix 定義完整角色/授權矩陣；admin toggle course permission、create/rotate/revoke CLI credential API。

## 9. Open text 安全投影 — 已定案（非阻擋部分延後）

**決策**：

- MVP backend 固定回傳**安全 plain-text list projection**：純文字、長度驗證、不接受 HTML/Markdown、API 安全編碼、不含 participant/display name（規劃 L57、M2 §2.6 L250-265）。
- 文字雲屬 frontend/後續產品能力，非 backend 責任。
- vote-to-reveal：題目 open 時 learner 需先作答才可見受限制 aggregate；題目 close 後全班可見最終結果（US-F17）。open_text 即時結果不得洩露不符合 vote-to-reveal 的資料。

**非阻擋**：文字列表/文字雲切換等視覺呈現為產品決策，不阻擋資料與 API（M2 §2.6 L381-389）。

**影響**：Phase 7 實作 open_text aggregate 安全投影。

## 10. Wire contract：REST /api/v1、UUID ID、UTC timestamp、穩定 error envelope — 已定案（基礎於 Phase 1）

**決策**：

- REST 路徑前綴 `/api/v1`，URI versioning（規劃 L54）。
- ID 為 UUID（決策 1）；timestamp 為 UTC ISO 8601。
- 穩定 error envelope：

  ```json
  {
    "error": {
      "code": "STABLE_CODE",
      "message": "human-readable",
      "field": "optional path",
      "blocking": true,
      "nextStep": "optional actionable"
    }
  }
  ```

  （M2 §2.5 L190-231 基線）

- 分頁格式、OpenAPI 完整定義留後續設計文件；Phase 1 實作 envelope 基礎與 `/api/v1` prefix。

**影響**：Phase 1 `src/common/http` global exception filter → envelope；Phase 2+ 各 API 遵循。

## 11. Redis 邊界 — 已定案

**決策**：Redis 僅用於 rate limit 與多 instance Socket.IO adapter，不作為 domain state / 帳號 / Session 的唯一權威來源（M2 §2.7、規劃 L159）。

**影響**：Phase 2 account+source 雙 rate limit 可用 Redis counter（或 DB fallback）；Phase 7 Redis adapter 協調多 instance；Phase 9 metrics。
