# M04 角色與功能對應管理—使用者需求與驗收規格

> **來源：**《即時互動教學系統 — 系統功能規劃書 V1.2》M04（角色與功能對應管理）及相關預設角色權限矩陣、資料模型與業務規則<br>
> **模組優先級：** P0<br>
> **規格狀態：** 已依需求決策更新；各模組完整 API／Action 權限映射及 M10 稽核細節仍依跨模組契約落實。

## 1. 需求概覽與假設

- **功能目標：** 提供系統管理者查詢系統可授權功能及角色目前權限、依最小權限原則維護角色—功能對應，並在每次受保護操作由後端驗證有效授權，確保角色設定可控、可追溯且不能僅靠前端隱藏功能繞過。
- **範圍：** 涵蓋 M04-01～M04-09：功能清單、功能分類、角色功能查詢、角色功能授權、角色功能取消授權、按角色批次儲存全部功能授權、後端功能存取檢查、權限變更紀錄及前端功能選單過濾。
- **V1 角色與權限：** 正式角色固定為 `SYSTEM_ADMIN`、`TEACHER`，由 M02 定義及管理；V1 不建立自訂角色。權限以模組為主要授權單位，模組至少區分讀取與寫入權限；權限代碼及語意由系統維護，不由本模組任意新增或改名。各模組負責列出納入該模組讀取／寫入範圍的 API／Action。
- **授權模型：** 採 `USER_ACCOUNT → USER_ROLE → ROLE → ROLE_PERMISSION → PERMISSION → API／Action` 三層授權鏈。有效授權須同時考量帳號狀態、角色指派、角色狀態及角色功能對應。持有多個有效角色時採權限聯集：任一有效角色授予即滿足功能權限；不採 deny 覆寫。仍須通過資源擁有者／活動主持者與業務狀態檢查。
- **預設權限原則：** 新增／變更角色權限以最小權限為原則。`SYSTEM_ADMIN` 預設可使用系統管理功能；`TEACHER` 預設僅可使用老師功能。系統管理者不因 `SYSTEM_ADMIN` 自動取得 `TEACHER` 授課功能；若需授課須另指派 `TEACHER`，並由兩角色的有效權限聯集計算。
- **權限異動：** 授權與取消授權均由具備相應權限的系統管理者執行；按角色一次提交該角色完整的權限集合，必須全有全無，不得部分儲存。異動成功後不立即改變既有登入 Session 的權限快照；使用者重新登入後才套用新映射。停用帳號／角色的即時撤權仍遵循 M01／M02 契約。
- **最後管理者保護：** `SYSTEM_ADMIN` 映射可由授權管理者調整，但至少須保留一位啟用的系統管理者具備角色授權維護、帳號管理及稽核檢視能力。此核心能力檢查及映射更新須原子完成，涵蓋並行異動。
- **關聯模組：** M01 負責帳號啟用狀態及登入憑證；M02 負責固定角色定義、狀態及角色清單；M03 負責帳號角色指派與老師帳號生命週期；M05～M09、M11 提供各功能所需的操作權限與資源層級授權；M10 負責稽核政策。
- **範圍界線：** M04 維護 `ROLE_PERMISSION`，不建立／修改／刪除角色、不管理帳號角色指派，也不取代各功能模組的資源擁有者檢查。前端選單過濾只是使用體驗，並非安全控制。

## 2. 功能範圍

| 功能 ID | 功能名稱 | 功能說明 | 範圍界線 |
|---|---|---|---|
| M04-01 | 功能清單 | 列出依模組分類的讀取／寫入權限及其代碼。 | 顯示系統定義的權限目錄；不在管理介面建立或任意更名權限代碼。 |
| M04-02 | 功能分類 | 依帳號、老師、題庫、活動、報表、分組／競賽及系統管理等模組分類。 | 分類服務於查詢與呈現，不改變權限語意。 |
| M04-03 | 角色功能查詢 | 查詢 `SYSTEM_ADMIN`、`TEACHER` 目前被授予的功能。 | 僅授權管理者可查看完整映射；回傳角色及權限狀態，不回傳認證秘密。 |
| M04-04 | 角色功能授權 | 將一項或多項已定義的模組讀取／寫入權限授予指定角色。 | 僅可操作存在且啟用的固定角色及 V1 可用的系統定義權限；停用中的 P1 權限不可指派。 |
| M04-05 | 角色功能取消授權 | 移除指定角色的既有功能授權。 | 須防止撤銷最後一位有效管理者的必要管理能力。 |
| M04-06 | 權限批次儲存 | 一次提交指定角色的完整權限集合。 | 全有全無；採最後寫入者勝；每次實際套用均稽核記錄被取代的前後值。 |
| M04-07 | 功能存取檢查 | 後端 API／Action 檢查使用者是否具備有效權限。 | 每次受保護請求均須驗證帳號、角色、授權及必要的資源層級條件。 |
| M04-08 | 權限變更紀錄 | 依 M10 全域稽核政策記錄角色功能授權異動。 | 事件欄位、失敗事件及保存期限均依 M10 定義；不得記錄憑證或秘密。 |
| M04-09 | 功能選單過濾 | 前端依有效權限顯示可操作選單及控制項。 | 僅為 UX；後端 API 必須獨立執行同等授權檢查。 |

## 4. 權限目錄範例

權限以模組為主要授權單位，預設代碼採 `<MODULE>_READ` 與 `<MODULE>_WRITE`；M01 本人資料採本人範圍，M04 權限設定及 M10 稽核另依管理者預設矩陣控管。規劃書列出的細部代碼為功能案例，實際映射至所屬模組權限；各模組須在契約中明列其讀取／寫入範圍及必要的資源限制。

| 模組權限代碼範例 | 涵蓋功能案例 | 關聯模組／額外限制 |
|---|---|---|
| `M03_READ` | `TEACHER_READ` 等老師查詢功能 | M03；限核定管理範圍 |
| `M03_WRITE` | `TEACHER_CREATE` 及其他老師帳號維護 | M03；依帳號狀態、最後角色及最後管理者規則檢查 |
| `M04_READ` | 查詢權限目錄及角色映射 | M04；限授權管理者 |
| `M04_WRITE` | `ROLE_PERMISSION_UPDATE` 及批次儲存映射 | M04；限授權管理者並保護最後管理能力 |
| `M05_WRITE` | `QUESTION_SET_CREATE` 及題庫維護 | M05；另檢查題庫擁有者範圍 |
| `M06_WRITE`／`M07_WRITE` | `SESSION_HOST`、`SESSION_CONTROL` | M06／M07；限活動主持老師及允許的活動狀態 |
| `M09_READ` | `REPORT_READ`、`TEAM_SCORE_READ` | M09／M11；限自己的活動或其他明確授權範圍，並遵循排行榜公布狀態 |
| `M06_WRITE`／`M11_WRITE` | `SESSION_GROUPING_CONFIGURE`、`TEAM_RANDOM_ASSIGN`、`TEAM_MEMBER_UPDATE`、`TEAM_COMPETITION_CONTROL` | M06／M07／M11；檢查首次計分前、`TEAM` 模式及活動範圍條件 |
| `M11_ORGANIZATION_COMPETITION_WRITE`（P1，V1 停用） | `ORGANIZATION_COMPETITION_MANAGE` | M11；V1 不可指派或通過授權檢查，P1 上線時再啟用 |

## 5. 使用者故事

> **身為**具備角色功能授權管理權限的系統管理者，<br>
> **我希望**檢視系統功能權限目錄及角色目前授權，並一次維護指定角色的完整權限集合，<br>
> **以便於**依最小權限原則管理功能存取，確保每項受保護操作都由後端正確授權且變更可追溯。

## 6. 驗收條件

```gherkin
Feature: M04 角色與功能對應管理

  Background:
    Given 管理者已登入且帳號為啟用狀態
    And 管理者具備目前操作所需的 M04 權限

  Scenario: 查詢系統功能權限目錄
    When 管理者查詢可授權功能
    Then 系統回傳依模組分類的讀取／寫入權限代碼
    And 每項權限包含代碼、名稱或說明及所屬功能分類
    And P1 停用權限須清楚標示且不可指派
    And 系統不得回傳密碼、Session／Token 或其他認證秘密

  Scenario: 依模組查詢讀取／寫入權限
    Given 權限目錄依帳號、角色、老師、題庫、活動、報表、競賽及系統管理等模組分類
    When 管理者查詢其中一個模組
    Then 系統回傳該模組可授權的讀取／寫入權限及其操作範圍
    And 分類查詢不得改變任何角色授權

  Scenario: 查詢角色目前功能授權
    Given 指定角色為 V1 固定角色 `SYSTEM_ADMIN` 或 `TEACHER`
    When 管理者查詢該角色功能授權
    Then 系統回傳該角色目前完整的有效權限集合
    And 權限清單可區分已授權與未授權項目
    And 查詢不建立或修改 `ROLE_PERMISSION`

  Scenario: 授予角色一項功能權限
    Given 指定角色存在且啟用
    And 欲授予的權限代碼存在於系統權限目錄
    When 管理者提交包含該權限的角色完整權限集合
    Then 系統保存該角色的權限集合
    And 指定權限納入該角色映射，並於使用者重新登入後生效
    And 系統依 M10 政策記錄操作者、時間、角色及異動前後值

  Scenario: 取消角色功能權限
    Given 指定角色目前已授予某項功能權限
    And 移除後不會使平台失去最後一位具必要管理能力的有效管理者
    When 管理者提交不含該權限的角色完整權限集合
    Then 系統移除該角色對該功能的授權
    And 已建立的 Session 仍依其登入時權限快照判定
    And 使用者重新登入後，後端依最新設定拒絕未授權請求
    And 系統依 M10 政策記錄該異動

  Scenario: 一次批次儲存指定角色的完整權限集合
    Given 指定角色存在且管理者具有 `M04_WRITE` 權限
    And 提交的每一項權限均存在且可授權
    When 管理者提交該角色完整的權限集合
    Then 系統以全有全無方式保存全部新增及移除的對應
    And 不得只保存部分項目
    And 異動成功後既有 Session 保留登入時的權限快照
    And 使用者重新登入後，新 Session 依最新授權集合判定權限
    And 系統依 M10 政策記錄整體異動前後權限集合

  Scenario: 權限映射異動於重新登入後生效
    Given 使用者已持有以登入時角色映射建立的有效 Session
    And 管理者成功授予或撤銷該角色的一項模組權限
    When 使用者在既有 Session 中呼叫受保護 API
    Then 系統依既有 Session 的權限快照判定請求
    When 使用者登出後重新登入
    Then 新 Session 依最新角色權限映射判定請求

  Scenario: 批次儲存包含無效權限時整批失敗
    Given 管理者提交的權限集合含不存在、重複或不允許指派的權限代碼
    When 系統驗證該批次授權
    Then 系統拒絕整批儲存並指出可修正的項目
    And 角色原有 `ROLE_PERMISSION` 集合完全不變
    And 不得留下部分授權

  Scenario: V1 停用的 P1 權限不得指派或通過檢查
    Given `ORGANIZATION_COMPETITION_MANAGE` 已列入目錄但 V1 狀態為停用
    When 管理者提交含該權限的角色映射
    Then 系統拒絕整批儲存且既有映射保持不變
    When 使用者以該權限呼叫組織間競賽 API
    Then 系統拒絕該請求

  Scenario: 查詢不存在或非 V1 角色
    Given 指定角色代碼不存在或不是 V1 固定角色
    When 管理者查詢或更新該角色功能授權
    Then 系統拒絕該要求並回覆可辨識的不存在或不支援結果
    And 不建立角色或任何角色授權關聯

  Scenario: 未授權者不得查詢或修改角色功能授權
    Given 使用者未登入、帳號已停用或不具備相應 M04 權限
    When 使用者查詢完整權限目錄／角色映射或提出授權異動
    Then 後端拒絕該要求
    And 不回傳受限資料或執行異動
    And 前端隱藏功能不可取代後端授權檢查

  Scenario: 停用帳號或角色不得取得有效功能權限
    Given 使用者帳號停用、角色停用或帳號與角色的指派無效
    When 該使用者呼叫任何受保護 API
    Then 系統拒絕請求
    And 不因 `ROLE_PERMISSION` 中仍保留映射而授予有效權限

  Scenario: 未列入目錄的 API 動作預設拒絕
    Given API／Action 未設定有效的權限代碼或權限目錄資料無法驗證
    When 使用者呼叫該受保護 API
    Then 系統拒絕請求
    And 不得以缺少權限設定視為允許

  Scenario: 前端依有效權限過濾功能
    Given 使用者登入且已取得有效權限集合
    When 前端建立導覽選單及可操作控制項
    Then 前端只呈現符合有效權限的項目
    And 直接呼叫隱藏項目對應的 API 仍須由後端獨立驗證

  Scenario: 多角色使用者的權限計算
    Given 使用者有多個有效且啟用的角色
    And 某功能權限至少被其中一個有效角色授予
    When 使用者呼叫對應 API 且符合資源範圍條件
    Then 系統依多角色授權規則判定該功能權限有效
    And 使用者仍不得存取超出資源擁有者／主持者範圍的資料

  Scenario: 變更權限不得移除最後一位有效系統管理者的核心能力
    Given 平台僅剩一位啟用且持有 SYSTEM_ADMIN 的有效系統管理者
    When 管理者提交會撤銷其角色授權維護、帳號管理或稽核檢視能力的映射
    Then 系統拒絕該異動
    And 角色原有權限集合保持不變
    And 拒絕原因可供管理者理解且不得洩露認證秘密

  Scenario: 並行權限異動不得造成最後管理者失權
    Given 兩位管理者並行提交會移除核心管理能力的角色映射
    When 兩項更新同時進行
    Then 系統以原子方式檢查最後有效管理者保護條件
    And 依最後寫入者勝的規則套用通過檢查的更新
    And 任一成功更新均不得使平台失去受保護的核心管理能力

  Scenario: 同一角色權限採最後寫入者勝
    Given 角色映射在管理者甲讀取後已被管理者乙更新
    When 管理者甲稍後提交該角色完整權限集合且通過核心管理權限檢查
    Then 系統以管理者甲提交的完整集合取代目前映射
    And 稽核記錄實際被取代的映射及新映射
    And 系統不得留下部分權限集合

  Scenario: 權限服務或必要依賴不可用時採拒絕策略
    Given 權限目錄、角色映射或權限檢查服務無法完成驗證
    When 使用者呼叫受保護 API 或管理者提交授權異動
    Then 受保護 API 不得將無法驗證視為已授權
    And 權限異動不得回報成功或留下部分資料
    And 系統回覆可重試的服務錯誤，不洩露內部安全資料

  Scenario: 權限異動留下稽核紀錄
    Given 管理者提交角色功能授權變更
    When 異動成功或被拒絕
    Then 系統依 M10 政策記錄操作者、時間、目標角色、結果及必要原因
    And 成功異動記錄授權前後集合或等效差異
    And 不記錄密碼、Session／Token 或其他認證秘密
```

## 7. 欄位、資料與邊界規則

- **角色資料：** V1 只支援 M02 定義的 `SYSTEM_ADMIN`、`TEACHER` 固定角色；M04 不新增、修改角色代碼或刪除角色。
- **權限目錄：** 權限以模組為主要單位，模組讀取／寫入權限包含哪些 API／Action 由該模組契約明列。每個模組權限至少須有穩定唯一代碼、名稱／說明及模組分類；未列入目錄或無法解析的受保護動作預設拒絕。規劃書列出的細部代碼屬功能案例，映射至所屬模組讀取／寫入權限。V1 目錄由系統版本管理，不能透過授權介面任意新增或改名。
- **P1 權限：** `ORGANIZATION_COMPETITION_MANAGE` 在 V1 權限目錄中預先列出並標記停用；不可指派，且 API 即使收到該權限也必須拒絕。待 M11 P1 正式啟用後，依版本化目錄變更啟用。
- **角色功能對應：** `ROLE_PERMISSION` 關聯僅能引用既存的 `ROLE` 及 V1 可用 `PERMISSION`；同一角色與權限的重複關聯不得建立。一次儲存代表該角色完整有效權限集合，新增／撤銷需在同一原子操作中完成。
- **授權判定：** 必須驗證帳號啟用、登入憑證有效、至少一個有效指派角色啟用，且任一有效角色映射含所需模組權限；另需依資源層級規則確認資料擁有者或活動主持者。帳號停用、角色停用、指派無效、權限不存在或檢查服務失敗時一律拒絕。
- **多角色：** 多個有效角色採權限聯集；任一有效角色授予模組權限即可滿足功能層級檢查，不設顯式 deny。即使功能權限成立，資源範圍授權仍須另外檢查。
- **預設映射：** 初始權限依本文第 3 節角色矩陣及部署時的系統權限目錄建立；`SYSTEM_ADMIN` 不自動包含老師授課功能，需另授 `TEACHER` 角色。任何偏離預設的異動均須由授權管理者明確提交並依 M10 稽核政策記錄。
- **更新生效：** 成功授權變更不改寫已建立 Session 的權限快照；新映射於使用者重新登入後套用。帳號／角色停用造成的立即拒絕及憑證撤銷仍依 M01／M02 規則，不因本項一般映射生效時點而延後。
- **並行更新：** 同一角色映射採最後寫入者勝；後提交且通過驗證的完整集合取代目前映射。每次提交須以原子方式檢查最後管理者保護，稽核須記錄實際被取代的集合與新集合，不得部分儲存。
- **最後管理者保護：** 更新前後須保留至少一位啟用帳號、有效持有啟用 `SYSTEM_ADMIN` 角色，且仍具有角色授權維護、帳號管理及稽核檢視能力的管理者。保護檢查與映射更新須原子化。
- **稽核：** 權限異動事件格式、成功／失敗記錄範圍、保存期限及遮罩均遵循 M10；成功異動須可追查操作者、時間、目標角色及前後授權差異。不可記錄密碼、Session／Token、Cookie 或其他認證秘密。
- **學員與資源邊界：** 學員使用活動憑證，不建立正式角色或 `USER_ROLE`；老師角色權限不授予跨老師題庫、活動或報表存取，所有資源 API 需檢查擁有者／主持人範圍。

## 8. 非功能性需求

- **後端強制授權：** 每個受保護 API／Action 必須執行權限檢查；不能只靠前端選單過濾。漏設權限代碼、權限服務無法使用或資料無法驗證時採 fail-closed。
- **最小權限：** 初始角色映射遵循第 3 節矩陣；管理者不預設取得授課權；功能權限與資源範圍授權分層檢查。
- **一致性與原子性：** 角色權限集合儲存全有全無；最後管理者約束與變更需原子化。並行更新採最後寫入者勝，且實際前後值均依 M10 留痕；不得讓有效管理者失去受保護的核心功能。
- **安全生效：** 一般權限映射變更於使用者重新登入後生效；舊 Session 沿用登入時權限快照。帳號或角色停用等即時撤權規則仍依 M01／M02 契約執行。
- **資料隱私：** 權限目錄及角色映射查詢僅提供授權管理所需資訊，不回傳任何帳號密碼或認證憑證。
- **可稽核性：** 權限映射異動可依 M10 追查操作者、時間、角色、異動內容及結果；稽核不得包含認證秘密。
- **可用性與效能：** V1 權限目錄規模及角色數由系統定義；查詢及存取檢查效能門檻沿用平台整體 NFR，不在 M04 自行假設未核定數值。

## 11. 跨模組契約事項

- **M01 帳號與登入：** 提供帳號有效狀態及登入憑證驗證；一般角色權限映射變更於重新登入後生效，既有 Session 依登入時的權限快照判定。停用帳號／角色造成的即時撤權仍依 M01／M02 規則執行。
- **M02 角色管理：** 提供固定角色代碼及啟停用狀態；角色停用後其 `ROLE_PERMISSION` 不得再產生有效授權。M04 不改動角色基本資料或角色狀態。
- **M03 老師管理：** M03 負責 `USER_ROLE` 指派及老師管理操作；各 API 對應到 M03 模組讀取／寫入權限，再執行帳號、角色及資源層級檢查。角色授權維護不得取代 M03 的帳號生命週期規則。
- **M05～M09、M11 功能模組：** 各模組需定義本模組讀取／寫入權限涵蓋的 API／Action 清單，於後端 API 實際檢查；另自行驗證題庫擁有者、活動主持者、活動狀態、分組模式及排行榜公布狀態等業務限制。`ORGANIZATION_COMPETITION_MANAGE` 在 V1 停用，P1 啟用前不得授權或執行。
- **M10 系統設定與稽核：** 依全域稽核政策記錄角色功能授權異動及必要失敗事件，定義操作者、時間、角色、異動前後值、保存期間及遮罩規則。
- **平台共通契約：** 定義錯誤回應、存取拒絕、完整權限集合的最後寫入者勝語意、交易原子性、Session 權限快照及效能 SLA；依賴不可用時不得 fail-open。
