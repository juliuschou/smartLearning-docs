# M02 角色管理—使用者需求與驗收規格

> **來源：**《即時互動教學系統 — 系統功能規劃書 V1.2》M02（角色管理）及相關權限矩陣、資料模型與業務規則<br>
> **模組優先級：** P0<br>
> **規格狀態：** 需求決策已確認；跨模組實作細節依 M01、M03、M04、M10 及平台共通契約落實。

## 1. 需求概覽與假設

- **功能目標：** 讓獲授權的系統管理者查詢平台角色及其權限摘要、管理角色啟停用，並確保帳號角色指派規則一致，以維持清楚、可控的存取身分。
- **範圍：** 涵蓋 M02-01～M02-05：固定角色清單、角色明細、固定角色基本資料唯讀、角色狀態檢視與啟停用，以及正式帳號角色指派資訊檢視。帳號角色指派新增／移除由 M03 統一執行。
- **V1 角色：** 正式系統帳號角色為 `SYSTEM_ADMIN`（系統管理者）及 `TEACHER`（老師）。兩者為固定系統角色；角色代碼、名稱及描述不可修改，且不可刪除。角色可啟用或停用；停用後權限立即失效並撤銷受影響的既有 Session／Token，但保留帳號角色指派紀錄。自訂角色列為未來擴充，不納入本版。
- **指派原則：** 一個正式帳號可被指派一個或多個角色。系統管理者不因持有 `SYSTEM_ADMIN` 自動取得授課權；如需授課，須另行指派 `TEACHER`。
- **學員邊界：** 學員是單場活動的臨時參與者，不建立正式帳號，也不納入 M02 角色指派；其活動存取由活動憑證及 Session 控制。
- **關聯模組：** M01 負責帳號登入與認證狀態；M03 負責老師帳號生命週期及老師資料；M04 負責功能權限及角色—功能授權、後端權限檢查；M10 僅負責系統設定與營運活動監控。M02-05 的管理操作對象是正式帳號，不代表 M02 取代 M03 的老師管理流程。
- **角色狀態異動：** M02 負責固定角色啟用／停用；M03 負責帳號角色指派異動；M04 負責功能權限代碼、角色授權與各操作的權限檢查。M02 不新增、修改或撤銷角色功能授權。角色檢視、狀態變更及帳號指派各自所需的權限代碼由 M04 權限矩陣定義；授權管理者限符合該矩陣的系統管理者。

## 2. 功能範圍

| 功能 ID | 功能名稱 | 功能說明 | 範圍界線 |
|---|---|---|---|
| M02-01 | 角色清單查詢 | 固定顯示 `SYSTEM_ADMIN` 與 `TEACHER` 的代碼、名稱、說明、啟用狀態及系統保留標記。 | V1 固定兩筆，不提供搜尋、排序或分頁。 |
| M02-02 | 角色詳細資料 | 查看角色基本資料、狀態及 M04 提供的目前功能授權摘要。 | 僅顯示 M04 提供的授權資料及其狀態；授權服務不可用時依平台錯誤契約回覆，不得以空清單表示無授權。 |
| M02-03 | 角色說明維護 | V1 固定角色的代碼、名稱與描述皆不可修改；M02-03 不提供實際資料變更。 | 若未來開放可編輯欄位，須另行核定規則及權限。 |
| M02-04 | 角色狀態檢視與維護 | 顯示角色是否為系統保留角色及啟用／停用狀態，並允許具備 M04 所定權限的系統管理者啟用或停用角色。 | 停用角色立即撤銷受影響帳號的既有 Session／Token；帳號角色指派紀錄保留。 |
| M02-05 | 使用者角色指派 | 定義正式帳號可指派角色及狀態規則；指派資料由 M03 流程維護及呈現。 | V1 僅允許 `SYSTEM_ADMIN`、`TEACHER`；老師帳號透過 M03-09 指派 `TEACHER`。其他正式帳號的角色指派入口由 M03 帳號管理流程提供；M02 不直接寫入 `USER_ROLE`。 |

## 3. 使用者故事

> **身為**具備角色檢視及狀態管理權限的系統管理者，<br>
> **我希望**檢視固定角色與其功能授權摘要、管理角色啟停用，並透過 M03 流程維護帳號角色指派，<br>
> **以便於**依最小權限原則管理使用者的系統存取能力，且不把管理職責與授課職責混為一談。

## 4. 驗收條件

```gherkin
Feature: M02 角色管理

  Scenario: 獲授權的管理者查詢角色清單
    Given 使用者已登入且具備角色管理所需權限
    When 使用者查詢角色清單
    Then 系統回傳 V1 固定系統角色 SYSTEM_ADMIN 與 TEACHER
    And 每筆角色資料包含角色代碼、名稱、說明及系統保留狀態
    And 系統不回傳密碼、Session 憑證或其他非角色管理所需的敏感資料

  Scenario: 查詢角色詳細資料及功能對應
    Given 使用者已登入且具備角色檢視權限
    And 指定角色存在
    When 使用者查詢該角色明細
    Then 系統回傳角色基本資料及系統保留狀態
    And 系統呈現該角色目前對應的功能權限
    And 功能權限資料僅供檢視，其維護仍由 M04 負責

  Scenario: 查詢不存在的角色
    Given 使用者已登入且具備角色檢視權限
    And 指定角色代碼不存在
    When 使用者查詢角色明細
    Then 系統回覆可辨識的「角色不存在」結果
    And 系統不建立或修改任何角色資料

  Scenario: 角色功能授權資料服務不可用
    Given 使用者已登入且具備角色檢視權限
    And 角色明細服務無法取得 M04 的功能授權資料
    When 使用者查詢角色明細
    Then 系統回覆可重試的服務錯誤
    And 不得以空的功能清單表示該角色沒有授權
    And 不執行任何角色資料異動

  Scenario: 未授權使用者不得管理角色
    Given 使用者未登入、帳號已停用或不具備相應管理權限
    When 使用者查詢受限角色資料或提出角色異動
    Then 系統拒絕該要求
    And 不回傳非授權資料且不執行任何異動
    And 後端 API 執行權限檢查，不以隱藏前端功能取代授權

  Scenario: V1 固定角色基本資料不可修改
    Given V1 固定系統角色 SYSTEM_ADMIN 或 TEACHER 存在
    When 管理者嘗試修改角色名稱或描述
    Then 系統拒絕該異動
    And 角色代碼、名稱及描述保持不變

  Scenario: 不允許修改系統角色代碼
    Given 使用者已登入且具備角色資料維護權限
    When 使用者嘗試修改 SYSTEM_ADMIN 或 TEACHER 的角色代碼
    Then 系統拒絕該異動
    And 原角色代碼保持不變

  Scenario: 停用角色使權限及既有憑證立即失效
    Given 管理者具備 M04 所定角色狀態維護權限
    And 角色已指派給一個或多個帳號
    And 停用後每個仍啟用的帳號至少保有另一個啟用角色
    And 受影響帳號持有有效 Session 或 Token
    When 管理者停用該角色
    Then 系統將角色狀態設為停用
    And 該角色不再授予任何有效權限
    And 系統立即撤銷所有因該角色而獲權的受影響 Session 或 Token
    And 系統保留既有帳號角色指派，以供重新啟用時恢復
    And 後續角色與權限查詢均反映最新狀態

  Scenario: 停用角色不得使啟用帳號失去所有有效角色
    Given 角色已指派給至少一個啟用帳號
    And 該帳號沒有其他啟用角色
    When 管理者嘗試停用該角色
    Then 系統拒絕停用
    And 角色狀態及所有帳號角色指派保持不變
    And 管理者須先透過 M03 為受影響帳號指派其他啟用角色或停用該帳號

  Scenario: 重新啟用角色恢復有效指派
    Given 角色目前為停用狀態
    And 一個或多個帳號仍保留該角色指派
    When 具備 M04 所定角色狀態維護權限的管理者重新啟用該角色
    Then 系統將角色狀態設為啟用
    And 該角色重新納入新登入或重新驗證時的權限計算
    And 不恢復已撤銷的 Session 或 Token，受影響使用者須重新登入
    And 後續角色與權限查詢均反映最新狀態

  Scenario: 不允許刪除固定系統角色
    Given 系統角色 SYSTEM_ADMIN 或 TEACHER 存在
    When 使用者嘗試刪除該角色
    Then 系統拒絕該要求
    And 角色及其既有關聯保持不變

  Scenario: 系統管理者不自動取得授課能力
    Given 正式帳號只被指派 SYSTEM_ADMIN
    When 該帳號嘗試使用需要 TEACHER 角色與相應功能權限的授課功能
    Then 系統不得僅因 SYSTEM_ADMIN 身分授予授課能力

  Scenario: M03 流程為管理者另行指派老師角色
    Given 正式帳號已被指派 SYSTEM_ADMIN
    And 操作者具備 M03／M04 定義的角色指派權限
    When 操作者透過 M03 帳號角色管理流程為該帳號另行指派 TEACHER
    Then M03 保存該帳號的兩項角色關聯
    And 帳號授課能力仍須符合 M04 的功能授權及資源層級檢查

  Scenario: 帳號可具有多個角色
    Given 正式帳號存在且管理者具備角色指派權限
    When M03 流程為帳號指派一個以上有效角色
    Then 系統保存帳號與各角色的關聯
    And 查詢帳號角色時回傳目前有效指派
    And 使用者不得自行指派或提升自己的角色

  Scenario: 一般角色指派異動於重新登入後生效
    Given 使用者持有已登入的 Session 或 Token
    And M03 已新增或移除該使用者的角色指派，且未停用角色
    When 使用者在異動後以既有 Session 或 Token 呼叫受保護功能
    Then 系統依該 Session 或 Token 建立時的授權狀態處理請求
    When 使用者重新登入
    Then 新 Session 或 Token 依最新有效角色及 M04 權限計算存取能力

  Scenario: 停用角色不受既有權限快照延後
    Given 使用者持有因某角色而獲權的有效 Session 或 Token
    When 管理者停用該角色
    Then 系統立即撤銷受影響的既有 Session 或 Token
    And 該使用者須重新登入，且新憑證不得包含已停用角色的權限

  Scenario: 拒絕指派不存在或停用的角色
    Given 正式帳號存在且管理者具備 M03 角色指派權限
    When 管理者指派不存在或目前停用的角色
    Then 系統拒絕該要求
    And 帳號既有角色關聯不變

  Scenario: 不得移除帳號最後一個有效角色
    Given 正式帳號目前僅有一個已啟用角色的有效指派
    When 管理者透過 M03 嘗試移除該指派
    Then 系統拒絕該異動
    And 帳號仍保有該有效角色
    And 若要停止該帳號存取，須由 M03 帳號停用流程處理

  Scenario: 角色指派異動不得部分成功
    Given 正式帳號及欲指派角色均存在
    When 角色指派因驗證、資料儲存或必要依賴失敗
    Then 系統不留下部分角色關聯異動
    And 系統回覆可重試或可修正的失敗結果

  Scenario: 保護最後一位有效系統管理者
    Given 平台僅剩一個啟用帳號，且該帳號有效指派已啟用的 SYSTEM_ADMIN 角色
    When 管理者嘗試停用 SYSTEM_ADMIN、移除該帳號的 SYSTEM_ADMIN 指派，或透過 M03 停用該帳號
    Then 系統拒絕會使有效系統管理者數量降至零的異動
    And 角色狀態、帳號狀態及角色指派保持不變
    And 檢查與異動以原子方式完成，避免並行操作同時移除最後管理者

  Scenario: 學員不得透過 M02 取得正式角色
    Given 使用者僅持有單場活動的學員參與憑證
    When 使用者嘗試查詢或指派正式帳號角色
    Then 系統拒絕該要求
    And 不建立正式帳號或 USER_ROLE 關聯

  Scenario: 保護最後管理者的檢查避免並行競態
    Given 平台有兩個已啟用且持有 SYSTEM_ADMIN 的帳號
    And 兩位管理者分別嘗試停用對方帳號或移除對方的 SYSTEM_ADMIN 指派
    When 兩項異動並行提交
    Then 系統必須以原子方式檢查並提交管理者數量約束
    And 至多一項異動可成功，平台仍至少保留一個啟用中的 SYSTEM_ADMIN 帳號
```

## 5. 資料、欄位與邊界規則

- **角色資料：** 每筆角色至少包含角色代碼、名稱、描述、啟用／停用狀態及系統保留標記。V1 只有兩筆固定系統角色；代碼、名稱、描述不可修改，角色不可刪除。狀態為可變欄位。
- **固定角色範圍：** V1 僅有 `SYSTEM_ADMIN`、`TEACHER`；自訂角色建立及新增角色種類不在本版範圍。M02-03 為來源功能項目，但 V1 不提供角色基本資料編輯操作。
- **角色狀態：** 啟用角色可參與新登入／重新驗證的授權計算；停用角色不再授權，並立即撤銷受影響帳號的既有 Session／Token。停用不刪除 `USER_ROLE` 指派；重新啟用後保留的指派恢復參與新憑證的權限計算，但不恢復已撤銷的憑證。停用前須檢查所有仍啟用且指派該角色的帳號，若任一帳號停用後將沒有任何啟用角色，須先經 M03 重新指派其他啟用角色或停用該帳號，否則拒絕停用；另須通過最後管理者保護檢查。
- **角色指派：** 角色指派關聯引用既存正式帳號與角色；V1 僅可指派 `SYSTEM_ADMIN`、`TEACHER`，不得指派不存在或停用的角色。重複新增相同指派採冪等處理，不得產生重複關聯。帳號可持有多個角色；同時持有兩個固定角色允許。指派新增／移除由 M03 統一執行；M03-09 管理老師帳號指派，其他正式帳號的指派亦須走 M03 帳號角色管理流程。帳號停用由 M03 處理。有效角色定義為「帳號仍啟用、角色狀態為啟用且 USER_ROLE 指派有效」；每個啟用正式帳號至少須有一個有效角色，不得移除帳號最後一個有效角色。停用角色亦不得使啟用帳號失去所有有效角色。
- **多角色授權：** `USER_ROLE` 關聯由 M03 的角色指派流程管理；`ROLE_PERMISSION` 關聯由 M04 管理。一般角色指派新增／移除在使用者重新登入後生效，既有 Session／Token 沿用登入時的權限快照；角色停用是例外，立即撤銷受影響憑證。新 Session／Token 依最新有效角色及 M04 權限計算。
- **最後管理者保護：** 至少保留一個符合以下全部條件的管理者：帳號啟用、`SYSTEM_ADMIN` 角色啟用，且帳號具有有效的 `SYSTEM_ADMIN` 指派。停用角色、移除管理角色指派或停用帳號均不得令符合條件的管理者數量降至零；檢查與異動須原子執行，並行操作時以仍符合條件的帳號數量為準。
- **資料完整性與隱私：** 角色啟停用及帳號角色指派異動須原子完成；重複冪等請求不產生重複關聯或額外業務狀態變更。錯誤回應不得暴露密碼、Session 憑證或不必要的敏感資料。
- **服務失敗：** 驗證或儲存依賴無法完成時，不得視為成功；異動需具原子性，錯誤回應不得洩露敏感資訊。

## 6. 非功能性需求

- **授權安全：** 角色清單／明細須由 M04 定義的檢視權限保護；角色啟停用須由 M04 定義的角色狀態維護權限保護；帳號角色指派權限由 M03／M04 契約定義。所有 API 均須由後端驗證登入狀態、帳號狀態及所需權限。前端控制僅為操作體驗，不構成安全邊界。
- **最小權限：** `SYSTEM_ADMIN` 不自動代表 `TEACHER`；授課能力須由明確角色及 M04 功能權限共同決定。老師可存取的題庫、活動及報表仍須執行資源層級授權。
- **完整性：** 角色代碼唯一；帳號角色關聯不得指向不存在的角色或帳號；角色及角色指派更新不得產生部分成功或靜默覆寫。
- **隱私：** 查詢僅回傳角色管理所需欄位；不可暴露密碼、認證憑證或非必要個人資料。
- **效能與容量：** V1 固定列出兩筆角色資料，不提供搜尋、排序或分頁；回應時間及同時管理者容量沿用平台整體 NFR，不另訂 M02 專屬門檻。

| Q02 | 固定系統角色名稱與描述 | `SYSTEM_ADMIN`、`TEACHER` 的名稱與描述皆不可修改；代碼亦固定。 |
| Q03 | 角色狀態定義 | 角色可啟用／停用。 |
| Q04 | 停用已指派角色的影響 | 權限立即失效並撤銷受影響的既有 Session／Token；保留帳號角色指派紀錄。若會使啟用帳號失去全部有效角色，須先經 M03 處理帳號指派或停用狀態，否則拒絕停用。 |
| Q05 | `SYSTEM_ADMIN` 與 `TEACHER` 能否並存 | 允許同一帳號同時持有兩種角色。 |
| Q06 | 帳號最後一個有效角色 | 有效角色須為啟用狀態且有效指派；禁止移除最後一個有效角色，也不得透過停用角色令啟用帳號失去全部有效角色。若需停止存取，交由 M03 停用帳號。 |
| Q07 | 最後管理者保障 | 至少保留一個帳號啟用、`SYSTEM_ADMIN` 角色啟用且指派有效的管理者；檢查涵蓋角色停用、角色移除及帳號停用，並以原子方式避免並行競態。 |
| Q08 | 權限變更生效時點 | 一般角色指派／移除於重新登入後生效；停用角色為立即撤權例外，須即時撤銷受影響既有 Session／Token。角色重新啟用後，保留指派只納入新登入／重新驗證的授權計算，不恢復已撤銷憑證。 |
| Q10 | V1 角色清單功能 | 固定列出兩種角色，不提供搜尋、排序或分頁；效能沿用平台整體 NFR。 |

## 8. 跨模組契約事項

以下項目不改變已確認的 M02 業務決策，由相鄰模組或平台共通規格具體化：

- **M04 權限代碼：** 為角色清單／明細檢視、角色啟停用分別定義並套用權限代碼；M03 角色指派操作所需權限亦須與 M04 授權矩陣一致。不得以 `ROLE_PERMISSION_UPDATE` 等其他授權功能代碼未經核定地代替上述權限。
- **M03 帳號角色指派：** 老師帳號依 M03-09 指派 `TEACHER`；其他正式帳號（例如系統管理者帳號）的新增／移除操作亦由 M03 帳號角色管理流程執行，不由 M02 直接寫入 `USER_ROLE`。
- **M01 Session／Token：** 一般角色指派異動依已確認規則於重新登入後生效；角色停用例外，須立即撤銷受影響憑證。撤銷介面及失效傳播方式由 M01／認證服務契約定義，不能弱化本規格的即時撤權要求。
- **平台共通契約：** 錯誤回應格式及服務不可用處理遵循平台 API 契約；效能門檻沿用平台整體 NFR。

## 9. 來源規則與關聯

- **M02 原始功能：** M02-01～M02-05，來源規劃書第 199–221 行。
- **預設角色與最小權限矩陣：** `SYSTEM_ADMIN` 不預設授課；如管理者需授課須另指派 `TEACHER`，來源規劃書第 296–322 行。
- **資料模型：** `ROLE`、`USER_ROLE`、`ROLE_PERMISSION` 分別承載角色、帳號角色關聯及角色功能授權，來源規劃書第 590–625 行。
- **關聯業務規則：** BR-001（系統管理者管理老師帳號與角色功能授權）、BR-003（帳號可有多角色且不得自行升權）、BR-004（停用帳號不得存取）、BR-005（前端及後端均落實權限），來源規劃書第 645–654 行。
- **相關模組：** M01 帳號與登入管理；M03 老師維護與管理；M04 角色與功能對應管理；M10 系統設定與活動監控。
- **學員邊界：** 學員以活動憑證參與，不納入正式帳號角色管理，來源規劃書第 389 行。
