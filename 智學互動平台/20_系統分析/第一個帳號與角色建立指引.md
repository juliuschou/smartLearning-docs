# 第一個帳號與角色建立指引

## 目的

在全新環境建立第一個可登入的正式帳號，並確保平台有可管理系統的管理者角色。這是初始化／部署程序，不是一般公開註冊流程。

## 已確認的需求規則

- V1 正式帳號角色只有固定系統角色 `SYSTEM_ADMIN`（系統管理者）與 `TEACHER`（老師）；代碼、名稱及描述不可修改，也不可刪除。
- 帳號由系統管理者透過 M03 建立或維護；正式帳號至少須有一個有效角色。
- 初始管理者帳號需指派已啟用的 `SYSTEM_ADMIN`，才能管理後續正式帳號與角色。
- `SYSTEM_ADMIN` 不會自動取得授課權；若初始帳號也要授課，需另外指派 `TEACHER`。
- 學員是單場活動的臨時參與者，不建立正式帳號。
- 平台任何時候至少須保留一個啟用帳號，且具有有效 `SYSTEM_ADMIN` 指派及啟用中的 `SYSTEM_ADMIN` 角色。

## 建立順序

> 以下是依現行需求規格整理出的安全初始化流程。實際 CLI、管理介面、資料庫 migration／seed 指令尚未在文件中定義，實作時應依部署工具補上，不要猜測或直接手動寫資料庫。

1. **部署初始化角色**：由受控的部署／初始化程序建立或確認固定角色 `SYSTEM_ADMIN` 與 `TEACHER`，兩者初始狀態為啟用。若角色及其權限定義已由 seed／migration 建立，不重複建立。
2. **初始化第一個管理者帳號**：僅允許於部署／維運時，透過 CLI 或部署工作執行獨立、受控的 bootstrap 建立流程；成功建立後須停用該 bootstrap 入口。實際指令名稱、可執行身分及停用機制依部署／維運契約落實。Email 為登入識別，帳號狀態依核定的 bootstrap 流程設定。不要提供未受保護的公開註冊入口，也不要將預設密碼或秘密寫入版本控制、日誌或容器 metadata。
3. **指派管理角色**：建立初始管理者帳號及指派有效的 `SYSTEM_ADMIN` 必須在同一筆資料庫交易中完成，並確保 bootstrap 完成時帳號與角色均啟用且 `USER_ROLE` 關聯成功。任一環節失敗時整筆交易回滾，不得留下可登入的半完成狀態；部署實作須確保相關資料操作共用同一交易邊界。
4. **安全交付憑證**：以 bootstrap 專用且核准的安全方式交付初始憑證；其格式、交付管道、到期及首次登入處理仍待本指引／部署契約核定。此 bootstrap 流程不等同於 M03 老師帳號邀請，也不使用 M01 忘記密碼重設連結替代；不得在文件或一般日誌中保存明文密碼。
5. **驗證**：確認該帳號可登入、有效角色包含 `SYSTEM_ADMIN`，並能通過後端授權檢查；確認帳號與角色狀態已正確建立，不記錄密碼或 Session／Token。
6. **後續帳號管理**：第一位管理者登入後，透過 M03 建立其他正式帳號並依最小權限指派角色。老師帳號依 M03-09 指派 `TEACHER`；管理者若需授課，也須明確加派 `TEACHER`。

## 安全與故障處理

- Bootstrap 僅允許於受控部署／維運環境透過 CLI 或部署工作執行；第一個管理者成功建立後必須停用該入口，不得在一般執行期持續暴露建立管理者的能力。
- 初始化需具冪等性：重跑時不得建立多個非預期的初始管理者或重複角色關聯；對既有帳號／角色應先檢查狀態並安全停止或回報。
- 任何失敗都不得回報成功；帳號建立及 `SYSTEM_ADMIN` 角色指派須於同一筆資料庫交易原子完成，失敗時全部回滾。
- 不得移除或停用平台最後一個有效 `SYSTEM_ADMIN`。若要輪替初始管理者，先建立並驗證另一位管理者，再停用或移除舊帳號的管理角色。
- 若忘記初始管理者憑證，使用核准的帳號復原／受控維運程序；不得以繞過授權或直接修改線上資料作為一般流程。

## 待實作／待確認

- B1 已決議：bootstrap 僅允許於部署／維運時透過 CLI 或部署工作執行，成功建立第一位管理者後停用入口。專用指令／部署流程名稱、可執行身分及停用機制仍待部署契約補明。
- 初始管理者以 Email 作為登入識別（已決議）；憑證交付方式、啟用流程細節及密碼政策補充規則仍待本指引與部署契約核定。密碼政策依 M01 已確認基線及後續核定的補充政策。
- B3 已決議：預設角色權限以版本控制的 migration／seed 管理，並確保重跑冪等。M04 定義權限目錄、預設矩陣與映射語意；實際 seed 內容及部署驗證依相應規格落實。
- B2 已決議帳號建立及角色指派使用同一筆資料庫交易；部署實作須驗證所有相關資料操作都參與該交易，任一步驟失敗均回滾。
